\subsubsection{Diseño del hardware}

En la figura~\ref{fig:Arq_harware} se presenta la arquitectura del hardware desarrollado. Se incluyen todos los componentes descritos en las secciones anteriores. 

El sistema cuenta con dos antenas correspondientes a la comunicación GNSS y 4G. 

Como parte de la interfaz humano-máquina, se cuenta con una pantalla LCD de 16x2, dos botones para la indicación manual de estado ocupado/desocupado y dos pilotos que permiten visualizar el estado de ocupación actual.

\subsection{Diseño e implementación del firmware}

En esta sección se presentan las consideraciones de diseño y el proceso de implementación del firmware. 

\subsubsection{Diseño del firmware}

El propósito del firmware desarrollado es satisfacer los requerimientos de conectividad, administración del hardware e interfaz con el usuario. A continuación se describen las principales funcionalidades del firmware: 

\begin{enumerate}
 \item Comunicación por comandos AT-UART con el módulo SIM A7670SA, para realizar las funciones de conexión a Internet a través de la red celular, que asegure la conexión con el \textit{broker} MQTT.
 
 \item Comunicación a través de tramas NMEA por el puerto UART con el módulo Quectel L76. Para la recepción e interpretación de los datos de geolocalización de las constelaciones GPS y BeiDou. 
  
 \item Monitoreo de los botones de ocupación a través de interrupciones y visualización de los estados de ocupación a través de los pilotos. 
 
 \item Generación de interfaz visual a través de la comunicación I2C con la pantalla LCD 16x2. 
 
 \item Administración de la energía del sistema a través de los modos de bajo consumo. 
 
 \item Administración de los recursos del microcontrolador a través de la implementación del sistema operativo en tiempo real FreeRTOS. 
\end{enumerate}

\subsubsection{Arquitectura del firmware}
\label{sec:arquitectura_firmware}

De acuerdo con lo planteado anteriormente, en la figura~\ref{fig:arq_firmware} se presenta un diagrama de componentes UML, que representa la arquitectura del sistema general, con énfasis en los componentes del firmware. 

En este diagrama (figura~\ref{fig:arq_firmware}) se representan como subsistemas (\textit{Subsystem}) los componentes de hardware como la ESP32, la pantalla LCD, el módulo 4G SIM A7670SA, los botones y los pilotos. Así mismo, se entienden como subsistemas los componentes de firmware proporcionados por el fabricante del microcontrolador, que corresponden a los drivers GPIO, UART y el bus I2C. Además, se hizo necesaria la implementación de una biblioteca propia para el control de la pantalla LCD a través del bus I2C.

De acuerdo con esto, los componentes del firmware se establecen en la ESP32, que corresponde al dispositivo programable encargado de realizar el control general del sistema.

	\centering
	\includegraphics[width=1\textwidth]{./Figures/Arquitectura_firmware_TFE_GNSS.png}

En el diagrama de la figura~\ref{fig:arq_firmware} se presentan los componentes de firmware más relevantes del sistema y la forma en que interactúan entre ellos. A continuación, se describe la funcionalidad de cada componente del firmware:

\begin{enumerate}
	\item El firmware inicia con la tarea \verb|init_mqtt_server_task()|, resaltada con color rojo, que se encarga de tres funciones primordiales: realizar la inicialización de los servicios MQTT que proporciona el módulo 4G (SIM A7670 SA), realizar la conexión con el \textit{broker} MQTT remoto y, si todo sale bien, desencadena la creación de las demás tareas del sistema. Esta tarea utiliza líneas de comandos AT para comunicarse con el módulo 4G.
	
	\item Tarea \verb|collect_data_task()| se encarga de recibir, a través de colas, la información relacionada con la ocupación y la posición de la cava. Dicha información proveniente de la tarea \verb|gnss_task()| y del manejador de interrupciones \verb|occupancy_isr_handler()|, respectivamente. Luego transmite a la tarea \verb|transmit_to_server_task()| la información recibida, a través de la cola \verb|cava_data_queue|.
	
	\item Manejador de interrupción \verb|occupancy_isr_handler()|, resaltada con color amarillo, es la función que se ejecuta siempre que ocurra una interrupción debida a los botones de ocupación de la cava, a saber, ocupado-desocupado. Este manejador de interrupción detecta qué botón se presionó y comunica a la tarea \verb|collect_data_task()| el estado de ocupación, a través de la cola \verb|occupancy_queue|. Además, esta tarea genera una acción de \textit{wakeup} del sistema cuando se encuentra en modo ahorro de energía. 	
	
	\item Tarea \verb|gnss_task()|, se encarga primordialmente de detectar la recepción de una trama NMEA del tipo GNRMC, lo que asegura que la posición ha sido calculada con señales de dos o más constelaciones satelitales; en este caso, GPS y BeiDou. La detección de tramas se realiza a través de interrupciones del módulo UART de la ESP32. Esta tarea descarta todas las tramas que no sean compatibles con el estándar NMEA y todas las que no sean del tipo GNRMC. Además, se encarga de la extracción de la información de las tramas RMC a través de la función \verb|nmea_rmc_parser_r()|. Esta última es una implementación de tipo \textit{thread-safe} para asegurar la compatibilidad con FreeRTOS. Además, comunica la posición actual a la tarea \verb|collect_data_task()|, a través de la cola \verb|position_queue|. Por último, esta tarea verifica si la posición no ha cambiado en los últimos 5 minutos, en caso de no cambiar, colocará al sistema completo en modo ahorro de energía. 
		
	\item Tarea \verb|transmit_to_server_task()|, se encarga de ejecutar la secuencia de transmisión de datos a través del protocolo MQTT, con el módulo 4G. La comunicación entre microcontrolador y el módulo se realiza a través de comandos AT. Esta tarea recibe los datos provenientes de la tarea \verb|collect_data_task()|, los transmite hacia el \textit{broker} MQTT en la nube con la función \verb|transmit_msg_mqtt()|. Al finalizar, construye un paquete de información con los datos de ocupación, posición y resultado de la transmisión MQTT, para ser transferido a través de la cola \verb|lcd_queue| hacia la tarea \verb|lcd_task()|. 
		
	\item Tarea \verb|lcd_task()| se encarga de administrar adecuadamente el acceso a los recursos de la pantalla LCD, para evitar sobrescritura o pérdida de información relevante que deba ser mostrada a través de la pantalla LCD. 
\end{enumerate}



\subsubsection{Implementación del firmware}
\label{sec:implementacion_firmware}

El firmware se implementó en el \textit{framework} ESP-IDF desarrollado por la empresa ESPRESSIF, para las series de SoCs ESP32, ESP32-S y ESP32-C. Este \textit{framework} proporciona un SDK apto para el desarrollo de cualquier aplicación genérica en estas plataformas, a partir de lenguajes de programación C y C++. Además, está optimizado para aplicaciones de Internet de las Cosas (IoT, del inglés \textit{Internet of Things}). 

También se utilizó el entorno de desarrollo (IDE) \textit{PlatformIO}, que se ejecuta como una extensión nativa en el IDE de \textit{Visual Studio Code}. \textit{PlatformIO} permite usar todas las funcionalidades de ESP-IDF de una manera fiable y ágil, sin enmascarar funcionalidades o configuraciones avanzadas del \textit{framework}. Además, permite ejecutar las versiones más estables de ESP-IDF, proporciona soporte por la comunidad de desarrolladores, es multiplataforma y de software libre. 

Para la implementación del firmware se utilizó el lenguaje de programación C y se implementó el sistema operativo en tiempo real FreeRTOS. Una ventaja importante que ofrece ESP-IDF es que está desarrollado sobre FreeRTOS, por tanto, el firmware se ejecuta nativamente en este.

Por petición del cliente, la codificación correspondiente al firmware no podrá ser mostrada, sin embargo, se empleará pseudocódigo para sustentarla y no comprometer la calidad del trabajo desarrollado. 

\subsubsection{Flujo general del firmware}

El firmware tiene la capacidad de ejecutar multitarea, gracias a que se realizó una implementación con FreeRTOS. El flujo general del programa se muestra en las figuras \ref{fig:flujo_firmware_1}, \ref{fig:flujo_firmware_2} y \ref{fig:flujo_firmware_3}. El programa se dividió en tareas, que son funciones puntuales que ejecutan una acción concreta y colaboran entre sí para operar el sistema en su conjunto. Las diferentes tareas se ejecutan de forma independiente y existe un flujo de información que se sucede de una tarea a otra. Como mecanismo de comunicación entre tareas, se utilizan las colas. Este comportamiento del firmware es relevante desde el punto de vista en que el sistema puede estar recibiendo, procesando y transmitiendo datos de posicionamiento de manera casi concurrente.

En el diagrama de la figura \ref{fig:flujo_firmware_1}, se muestra la siguiente secuencia de acciones: 

\begin{enumerate}
\item Inicialización de todos los periféricos del hardware que son requeridos para operar con los módulos externos. Tal es el caso de los periféricos de comunicaciones UART e I2C. El periférico UART es utilizado para la comunicación entre los módulos SIM A7670SA \citep{A7670SA} (comunicación celular, sección \ref{sec:SIMA7670SA}) y el módulo Quectel L76 (recepctor GNSS, sección \ref{sec:QL76}).

\item Inicialización de los periféricos GPIO e instala el servicio de interrupciones, para preparar la captura de los estados de ocupación que se da a través de botones.

\item Inicialización del bus I2C que es requerida para la comunicación con la pantalla LCD. Luego de esto, ocurre la inicialización de la pantalla LCD, para mostrar al usuario toda la información del inicio del sistema.

\item Inicialización de las colas, que son los canales de comunicación entre las distintas tareas del programa y se crea la tarea \verb|init_mqtt_server_task()|, que se explica a continuación. 

\end{enumerate}

En el mismo diagrama de la figura \ref{fig:flujo_firmware_1} (bifurcación A), se muestra el flujo de la tarea \verb|init_mqtt_server_task()|, que realiza lo siguiente:

\begin{enumerate}
\item Inicializar los serivicios MQTT en el módulo SIM A7670SA, para luego iniciar la conexión con el \textit{broker} MQTT en la nube.

\item Si lo anterior ocurre sin problemas, se crean las demás tareas del sistema: \verb|gnss_task()|, \verb|collect_data_task()|, \verb|transmit_server_task()| y \verb|lcd_task()|.

\item El \textit{scheduler} de FreeRTOS empieza a gestionar la ejecución de las tareas creadas previamente y cambia entre ellas según su prioridad y el tiempo asignado. El código principal (la función \verb|main()|) ya no continúa su ejecución. Este punto se representa con la bifurcación B. 

\item Para finalizar, la tarea \verb|init_mqtt_server_task()| se elimina a sí misma con la función de FreeRTOS \verb|vTaskDelete()|. Esto, con el objetivo de liberar recursos del microcontrolador. 

\end{enumerate}

\subsubsection{Implementación de las tareas del sistema}


A continuación, se explica en forma de pseudocódigo la implementación de cada una de las tareas del sistema. 

En el código \ref{cod:init_mqtt_server_task}, se muestra el pseudocódigo que refleja la implementación de la tarea \verb|init_mqtt_server_task()|. La tarea espera a que el módulo SIMA7670 se encuentre listo para la comunicación por comandos AT, para esto, en la línea 3 se implementa un bucle que bloquea la tarea mientras espera el estado ``READY'' del módulo. Luego, en la línea 5,  se inicializan los servicios necesarios para operar con MQTT. Esto incluye la configuración de parámetros y la preparación de las conexiones. Después, en la línea 6 se realiza la conexión al servidor MQTT; esto asegura que el sistema pueda enviar y recibir mensajes a través de este protocolo. Si la conexión es exitosa, se continúa con la creación de las tareas del sistema (ver línea 9). Después de crear y poner en marcha las tareas del sistema, en la línea 14, se elimina la tarea \verb|init_mqtt_server_task()|, lo que implica la liberación de recursos. Si hay una falla en la conexión con el servidor, se realizarán un total de 3 intentos de conexión, además del intento inicial (ver línea 6). Si falla la conexión se reporta el problema por la LCD con la instrucción de la línea 17 y se procede a la eliminación de la tarea en la línea 18.


\begin{figure}[H]
\begin{lstlisting} 
init_mqtt_server_task()
{
	while ("READY" == SIM_A7670SA)
		Esperar
	Inicializar servicios MQTT en SIM_A7670SA
	while (4 == intentos)
		Conectar con broker MQTT en la nube
		if ("OK" == Conexion_Servidor)
			Crear tareas: 
				gnss_task()
				collect_data_task()
				transmit_to_server_task()
				lcd_task()
			Eliminar: init_mqtt_server_task
			break
		else
			Reportar por LCD: Falla conexion broker
			Eliminar: init_mqtt_server_task
}

\end{lstlisting}
\captionof{lstlisting}{Pseudocódigo de la tarea init\_mqtt\_server\_task().}
\label{cod:init_mqtt_server_task}
\end{figure}
 

En el código \ref{cod:gnss_task}, se presenta el pseudocódigo de la tarea \verb|gnss_task()|. La tarea espera cada evento del puerto \verb|UART_0| (ver línea 4) para procesar las tramas NMEA con datos provenientes del receptor GNSS, lo que se puede ver en la línea 5. Luego del procesamiento, envía la información extraída por la cola \verb|position_queue|, que es gestionada por la tarea \verb|collect_data_task()| (ver línea 7). En la línea 8, el sistema verifica si ha pasado un intervalo de tiempo de cinco minutos para comprobar tres cosas: 

\begin{itemize}
\item Sí: si se alcanzaron los cinco minutos y las posiciones son iguales, el sistema entra en modo de ahorro de energía.
\item No: si no se han alcanzado los cinco minutos y las posiciones son diferentes, el sistema vuelve al inicio del bucle.
\item No: si no han pasado cinco minutos, el sistema vuelve al inicio del bucle.
\end{itemize}

En el código \ref{cod:occupancy_isr_handler}, se presenta el pseudocódigo del manejador de interrupciones \verb|occupancy_isr_handler()|, que aunque no es una tarea mapeada en el \textit{scheduler} de FreeRTOS, cumple un papel primordial, puesto que permite capturar los eventos de los botones de ocupación del sistema. El manejador está asociado con la subrutina de interrupciones que se debe ejecutar cuando ocurre un evento de GPIO. Esta se activa cuando se presiona un botón y se captura cuál botón ha sido presionado (ver línea 4). Si el botón presionado es el de ``libre'' se actualiza el estado para indicar que el recurso está libre y se envía un estado ``libre'' a través de \verb|occupancy_queue|, como se muestra en las líneas 5 a 7. \subsection{Diseño de la interfaz web}

Para el diseño de la interfaz web, se tuvo en cuenta satisfacer la historia de usuario descrita en la planificación de este trabajo y que motiva al desarrollo de este componente: 

``Como usuario final quiero ver una página web con un mapa que me muestre la posición en tiempo real de todas las cavas y su estado de ocupación para realizar un seguimiento de estas y organizar la logística del reparto de productos en la cadena de frío''.

De acuerdo con lo anterior y con el análisis de la sección \ref{sec:mapas_web}, se escogió la biblioteca \textit{leaflet.js} \citep{leafletjs} para la creación de mapas en la web, debido a que la empresa Cloud Technologys SAS, integra sus desarrollos web con tecnologías web con JavaScript y a que en la etapa de desarrollo del producto no se requerirá incurrir en gastos para el despliegue en pruebas o en entornos relevantes. 

El desarrollo de la aplicación web se llevó a cabo siguiendo la arquitectura mostrada en la figura \ref{fig:arq_mqtt}.

\begin{figure}[htbp]
	\centering
	\includegraphics[width=.9\textwidth]{./Figures/arquitectura_MQTT.png}
	\caption{Arquitectura MQTT \protect\footnotemark.}
	\label{fig:arq_mqtt}
\end{figure}
\footnotetext{Imagen adaptada de: \url{https://www.emqx.com/en/blog/mqtt-5-introduction-to-publish-subscribe-model}}

En esta arquitectura, el centro de la comunicación es el \textit{broker} MQTT, donde se centralizan los mensajes de los \textit{publishers} para ser transmitidos hacia los dispositivos \textit{subscribers}, a través de canales específicos, llamados \textit{topic}. El \textit{broker} MQTT es responsable de recibir conexiones iniciadas por el cliente y reenviar mensajes enviados por el cliente a otros clientes elegibles \citep{MasteringMQTT}. 

Para este trabajo, se utilizó el \textit{broker} EMQX \citep{EMQX}, que es utilizado para aplicaciones de IoT \citep{MasteringMQTT}. La aplicación web, al igual que el hardware desarrollado, son clientes del \textit{broker} EMQX. El hardware es el encargado de publicar mensajes con los datos de geolocalización, estado de ocupación, validez de la posición, la hora y la referencia de la cava. Por otro lado, la aplicación web recibe dichos datos y los hace visibles al usuario a través de un mapa y otros elementos de visualización web.  

\subsection{Implementación de la interfaz web}

Para la implementación de la interfaz web, se utilizaron las siguientes tecnologías: 

\begin{itemize}
	\item HTML: se utiliza para estructurar la página web.
	\item CSS (Bootstrap): para dar estilo a la página y facilitar la implementación, ya que cuenta con componentes predefinidos.
	\item Lenguaje de programación JavaScript, sus características y bibliotecas. A continuación, se detallan las más relevantes para este trabajo: 
		\begin{itemize}
			\item jQuery: biblioteca de JavaScript utilizada para facilitar la manipulación del DOM, eventos y AJAX.
			\item Leaflet.js: biblioteca de JavaScript para mapas interactivos.
			\item mqtt.js: biblioteca de JavaScript para conectarse a un \textit{broker} MQTT, permite la comunicación en tiempo real entre el navegador y el \textit{broker}.
		\end{itemize}
	\item \textit{IDE Visual Studio Code} para realizar la codificación. 
	\item Docker como plataforma para la etapa de desarrollo, donde se ejecutó el EMQX.
	\item \textit{Broker} EMQX. 
\end{itemize}


\subsection{Metodología de la implementación}
\label{sec:met_web}

A continuación, se presenta el proceso llevado a cabo para la implementación de la interfaz web. 

\begin{enumerate}

		\begin{itemize}

En la figura \ref{fig:mockup} se observa la versión desarrollada por el autor. El programa declara un mapa (\verb|map|), un marcador (\verb|marker|), una lista para almacenar el rastro de posiciones (\verb|path|), y una variable para la línea que representará ese rastro (\verb|polyline|). A continuación, se configura una serie de opciones para conectarse al servidor MQTT, incluyendo el tiempo de espera para la conexión, el ID del cliente, el nombre de usuario, la contraseña y el parámetro \textit{keepalive}. Se definen las siguientes funciones: 

\begin{itemize}

\item La función \verb|init_map| inicializa el mapa utilizando \textit{OpenStreetMap}. Centra el mapa en la posición inicial (\verb|home|) y añade un marcador en esta posición. Además, crea un \verb|popup| para el marcador que muestra la latitud y longitud de la posición inicial.

\item La función \verb|get_cava_data| recibe datos de la cava, convierte las coordenadas de latitud y longitud de estos datos a números flotantes, y devuelve un objeto con estas coordenadas.

\item La función \verb|set_cava_position_map| se encarga de actualizar el mapa con la nueva posición de la cava. Primero, actualiza elementos HTML con los nuevos valores de latitud y longitud. Si ya existe un marcador, lo elimina del mapa. Luego, crea un nuevo marcador en la nueva posición y añade un \verb|popup| con la información de esta posición. Además, añade la nueva posición a la lista path y dibuja un rastro en el mapa con esta lista. Finalmente, ajusta la vista del mapa para centrarlo en la nueva posición.

\end{itemize}

El programa llama a \verb|init_map| para inicializar el mapa. Cuando el cliente MQTT se conecta, imprime un mensaje de ``Conectado'' y se suscribe al tema \verb|topic_cava|. Maneja eventos de reconexión e impresión de errores en caso de que falle la conexión. Cuando el cliente recibe un mensaje, convierte el mensaje a un objeto JSON, obtiene la posición de la cava utilizando \verb|get_cava_data|, y llama a \verb|set_cava_position_map| con esta posición para actualizar el mapa.

let cava_data;

function init_map(){
    
    map = L.map('map').setView([home.lat, home.lng], 13);
    //OpenStreetMap 
    var tile_map = L.tileLayer('https://tile.openstreetmap.org/{z}/{x}/{y}.png', {
        maxZoom: 19,
        attribution: '&copy; <a href="http://www.openstreetmap.org/copyright">OpenStreetMap</a>'
    });

    tile_map.addTo(map)

    marker = L.marker([home.lat, home.lng]).addTo(map);
    marker.bindPopup("<b>Posicion</b>"+"<br>"+"lat: "+home.lat.toString()+
                     "<br>"+" lng: "+home.lng.toString()+
                     "<br> CD"
                    ).openPopup();
}

function get_cava_data(cava_data) {

    let latitude = parseFloat(cava_data.lat);
    let longitude = parseFloat(cava_data.long);

    return { lat: latitude, lng: longitude };
}

function set_cava_position_map(position){
    
    document.getElementById('lat').textContent = "Lat: "+position.lat.toString();
    document.getElementById('lng').textContent = "Lng: "+position.lng.toString();
    
    if (marker) {
        map.removeLayer(marker);
    }

    marker = L.marker([position.lat, position.lng]).addTo(map);
    var popup_info = "<b>Posicion</b>"+"<br>"+position.lat.toString()+", "+position.lng.toString();
    marker.bindPopup(popup_info).openPopup();

    path.push([position.lat, position.lng]);

    var rastro = L.polyline(path, {color: 'blue'}).addTo(map);

    map.setView([position.lat, position.lng], 15);
}

init_map();

    client.subscribe(topic_cava, { qos: 0 }, function (err) {

        }
    })

client.on('reconnect', (error) => {
    console.log('reconectando:', error)

    console.log('Conexion fallida:', error)
});

client.on('message', (topic, message) => {
   
    current_cava_position = get_cava_data(JSON.parse(message.toString()));
    set_cava_position_map(current_cava_position);
});
